# 产品设计方案：《挪车！师傅》 Carpool Lane

> 版本 v1.1 · 2026-08-28 · 基于 docs/02 深度调研报告的结论推导
> 一句话：师傅的车被堵死了——顺路捎上乘客、掐准班车节奏、腾挪出一条生路，开出这条窄巷子。

## 〇、命名

- **中文名**：《挪车！师傅》——全民梗"师傅，麻烦挪下车"，动作（挪车）+人设（老师傅）双锚点
- **英文名**：**Carpool Lane**（副标题 *Unblock & Drive*）
  - Carpool = 顺路捎人（核心微创新机制），Lane = 车道/疏通，双机制各占一词
  - 英美常见交通词汇（HOV carpool lane），海外用户零解释成本
  - 查重记录（2026-08-28，Bing 全网 + Google Play 站内）：无同名游戏；结果均为拼车服务（BlaBlaCar 等）与 1996 年电影《Carpool》，与游戏品类无冲突
  - 弃用备选：Hop In（撞 Illumination 电影《Hop》品牌）

## 一、产品定位

| 维度 | 决策 | 依据 |
|---|---|---|
| 品类 | Rush Hour 滑块疏通 × 路径规划微创新 | 疏通品类 2026 H1 最大黑马（Arrows/Car Out/Screw 全线爆发）；CrazyGames 全站 #1 是挪车疏通；主办方 Arrows Go 同赛道 |
| 平台 | H5 单文件，PC/手机浏览器自适应 | 赛制要求；3 秒上手 |
| 受众 | 全年龄休闲玩家（35+ 友好） | 主办方产品矩阵验证的银发友好打法 |
| 主题 | 中国城市停车共鸣场景：小区窄巷→学校门口→写字楼→商场→机场高速 | 「师傅，麻烦挪下车」全民梗；与海外竞品形成文化差异 |
| 篇幅 | 50 关 = 5 章 × 10 关 | 实体版 Rush Hour 40 关 4 档难度对齐；King 每 episode 引入新机制的节奏 |

## 二、核心玩法（3 秒上手）

- **棋盘**：6×6 网格（后期章节扩至 7×7 / 双出口变体）
- **棋子**：横车只能横移，竖车只能竖移（Rush Hour 经典规则，零学习成本）
- **目标**：把师傅的车（红车）开出右出口
- **操作**：点击/拖动车辆滑动，支持一次滑多格（爽感来源）
- **结算**：星级评价——**3★ = 求解器最优步数**，2★ = 最优 +2 步内，1★ = 通关

## 三、微创新机制（经典机制碰撞，克制不堆料）

### 机制 A｜顺路捎人（第 2 章引入，核心差异化）

- 棋盘上出现乘客格（乘客站在某辆车旁边/某个车位）
- **红车必须先滑到乘客格相邻位置"捎上人"，出口道闸才解锁**
- 化学反应：把"腾出通道"升级为"规划路线"——玩家要为红车设计一条绕经乘客的路径，而乘客位置本身被其他车挡着，两个子问题互相纠缠
- 这是"合成大西瓜式"的碰撞：Rush Hour 的空间腾挪 × 送快递的路径规划，没有任何新规则，只有新化学反应

### 机制 B｜班车（第 3 章引入，风险机制，可砍）

- 部分车是"班车"，车顶有箭头：**你每走一步，它沿箭头走一格**（确定性，无随机）
- 化学反应：引入时序推理——"我走这步，班车会顶上那个缺口"，玩家开始借力班车而非只把它当障碍
- 风险控制：按主办方指南"先做 3 关"验证；若试玩反馈"烧脑不适"，降级为第 4 章装饰性机制或砍掉，50 关结构不受影响

### 机制阶梯（新元素每 5-8 关一个，每个配 4 关教学周期）

| 章节 | 关卡 | 新元素 | 首通失败率目标 | 最优步数带 |
|---|---|---|---|---|
| 1 小区窄巷 | 1-10 | 基础滑块教学；L6 三格卡车 | <5% → 10% | 6-10 |
| 2 学校门口 | 11-20 | 捎人（单乘客） | 10% → 25% | 10-16 |
| 3 写字楼 | 21-30 | 班车；L26 双乘客 | 25% → 35% | 14-22 |
| 4 商场卸货区 | 31-40 | 捎人+班车组合；固定墙；L36 7×7 大棋盘 | 35% → 40% | 18-28 |
| 5 机场高速 | 41-50 | 多乘客按序接送（乘客有编号，须顺序捎）；章末 Boss 关 | 40% → 50%（L50 可到 60%） | 22-35 |

每章内部节奏（阶梯+波浪）：3 升 1 缓 + 章末峰值；高难关后必跟缓冲关（PNAS streak-end rule）。

## 四、难度工程（本项目的灵魂 = AI 驾驭力证据链）

### 关卡生产管线

```
AI 生成候选关卡（按章节配置：尺寸/车数/乘客/班车）
  → BFS 求解器验证：可解性 + 最优步数 + 每车必要性（去掉任一车仍可解 = 剔除）
  → 解路径窄度分析（最优解簇宽度）：窄 = 人类感知难
  → 按最优步数带 + 窄度双维度筛选入档
  → 人工试玩抽检（每章抽 3 关）
  → 输出难度曲线图 → 写入设计文档与迭代日志
```

- 硬指标：**50 关 100% 可解、步数单调递进带、无一关存在"无关车辆"**
- 这条管线直接回应调研发现的机会缺口：头部产品"太简单/内容耗尽"，无人在 H5 休闲端做求解器背书的难度系统
- 迭代日志将保存：每版难度曲线对比图、被剔除关卡及剔除原因（数量本身就是迭代打磨的证据）

### 难度双指标（回应"最优步数 ≠ 人类难度"的研究结论）

1. 最优步数（客观难度骨架）
2. 解路径窄度（人类感知难度）：最优解附近 ±2 步内的可行解数量，越少越难

## 五、留存与元设计（照标杆抄作业）

| 标杆原则 | 落地设计 |
|---|---|
| 可视化登山路（Duolingo） | 5 章场景地图，50 关进度条 + 章节解锁动画（"下一站：写字楼"） |
| 金发姑娘难度 | 章内曲线见上表；2★阈值给非完美玩家留余地 |
| 峰终定律 | 章末关最有戏剧性；通关瞬间：道闸抬起 + 红车冲出 + 减速带颠簸音效 + 「师傅，稳！」toast |
| 连随时间增值（Duolingo） | 连续通关计数（streak），断关不清零但"今日首通"连续天数计数 |
| 原子会话（Duolingo） | 单关目标 60-150 秒；关卡内每次滑动都有即时微反馈（车辆位移惯性、喇叭声） |
| 每日回访钩子 | 每日挑战关（从题库按种子随机生成，可分享成绩图） |
| 损失厌恶（Toon Blast） | 提示次数（高亮一辆该动的车）：通关奖励，卡关消耗——持有后不敢浪费 |
| 大清除时刻（Toon Blast） | 连续正确移动的"行云流水"连击反馈（combo 计数 + 屏幕震动轻反馈） |

## 六、Juice / 表现层（不看美术 ≠ 不做手感）

- 视觉：扁平简约 + 高对比色（红车唯一红色，视觉锚点）；车辆 emoji 风格贴纸（🚗🚕🚙🚚），零美术依赖
- 动效：车辆滑动缓动、捎人时乘客上车动画、道闸开启动画、通关粒子
- 音效：引擎起步、喇叭、道闸、通关欢呼——全部用 WebAudio 合成或免费音源
- 中国场景化文案：每关一句师傅语录（"这谁停的车？""技术活儿，赏口饭吃"）——成本低、共鸣高

## 七、变现设计（仅文档层面，体现设计完整性）

- IAA-first：仅激励视频位（+5 提示 / 跳过卡点关 / 双倍星星），**永不打断式插屏**——直接回应品类最大差评源
- 依据：激励视频单价是其他格式 30-100 倍；Unblock Me 因广告轻保持 4.9★

## 九、三天执行计划（含验证门）

### Day 1（今天）：核心循环验证
1. 可玩原型 v0.1：基础滑块 + 出口判定（1 关）——验证手感
2. **验证门 G1（主办方"先做 3 关"法）**：做纯滑块 3 关自测——"还想继续吗？"否 → 回炉
3. 求解器（Node.js CLI）：BFS + 最优步数 + 必要性检查
4. 关卡格式定稿（JSON schema，为管线铺路）
5. 捎人机制原型 3 关 → **验证门 G2**：捎人是否增加"规划"乐趣而非拖沓回溯感

### Day 2：规模化生产
1. 关卡生成管线跑通 → 产出 50 关 + 难度曲线
2. 机制阶梯全量实现（班车按 G2 结论决定去留）
3. 元系统（章节地图/streak/星级/每日挑战）
4. 设计思路文档 + 迭代日志框架

### Day 3：打磨与交付
1. Juice 全量（动效/音效/通关动画）
2. 人工全 50 关试玩 + 曲线微调（记录每处调整）
3. 找 2-3 人试玩，记录反应，按主办方指南做最后迭代
4. 文档定稿 + 邮件打包（H5 文件 + 设计思路 + 迭代日志）
