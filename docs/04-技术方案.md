# 技术方案：《挪车！师傅》 Carpool Lane

> v1.1 · 2026-08-28 · 从交付物倒推（Working Backwards）
> 硬约束：8/31 邮件交付 H5 文件 + 两份文档；3 个工作日；单人 + AI 流水线；评审不看代码质量但看"好不好玩"——**技术的一切决策为手感、关卡质量、AI 驾驭力证据链服务**。

## 一、技术栈选型（一页决策记录）

| 决策点 | 选择 | 否决项与理由 |
|---|---|---|
| 运行时 | **原生 JS (ES Module) + Canvas 2D** | Phaser/PixiJS：单文件交付需打包引擎（数百 KB），我们动画简单，不值；DOM+CSS：大量车辆滑动动画会掉帧 |
| 交付形态 | **源码模块化开发 + build.js 无依赖拼接 → 单文件 `index.html`** | 直接单文件开发：3 天迭代到后期不可维护；Webpack/Vite：为拼接引构建链不值，30 行 Node 脚本够 |
| 求解器 | **Node.js CLI，BFS/双向 BFS** | 6×6 状态空间实测毫秒级；A* 无必要（状态空间小，BFS 已最优且天然求"最短路"） |
| 关卡数据 | **JSON 内嵌**（50 关 ≈ 30KB） | 外部加载：单文件交付不允许 |
| 音效 | **WebAudio 程序合成**（振荡器+噪声） | 音频文件：破坏单文件；免费音源 CDN：不可靠 |
| 美术 | **系统字体 + emoji 车辆贴纸 + Canvas 矢量绘制** | 图片资源：破坏单文件；评审不看美术 |
| 存档 | **localStorage**（进度/streak/星级/设置） | 无服务端，不上云 |
| 测试 | Node 内置 `node:test`（求解器/规则单元测试 + 关卡全量 CI 校验） | Jest：依赖链不值 |

## 二、核心架构决策：同源双端规则模块（本方案最重要的一条）

```
                    ┌─────────────────────────────┐
                    │        rules/  (纯逻辑)      │
                    │  board.js  move.js  goal.js  │
                    │  · 零 DOM / 零 Canvas 依赖    │
                    │  · ESM，Node 与浏览器同源    │
                    └──────────┬──────────────────┘
                ┌──────────────┴──────────────┐
        浏览器端 │                             │ Node 端
    ┌───────────▼───────────┐      ┌──────────▼───────────┐
    │ 游戏：渲染/输入/动效/音 │      │ 工具：生成/验证/曲线  │
    │ + 内置提示(BFS 同款)   │      │ solver.js pipeline.js │
    └───────────────────────┘      └──────────────────────┘
```

**玩家玩的移动规则和求解器验证的移动规则是同一份代码**——杜绝"求解器说 3★是 12 步、游戏里却算 14 步"这类口径漂移；也让"内置 AI 提示"功能零成本复用求解器。这一条同时是工程保障和评审维度上"AI 驾驭力"的叙事支点。

## 四、数据结构

### 关卡 schema（v1）

```json
{
  "id": 23,
  "chapter": 3,
  "name": "早高峰·电梯口",
  "w": 6, "h": 6,
  "exit": {"x": 6, "y": 2},              // 右出口所在行
  "cars": [
    {"id": "R", "x": 1, "y": 2, "len": 2, "dir": "h", "role": "hero"},
    {"id": "c1", "x": 3, "y": 0, "len": 3, "dir": "v"},
    {"id": "b1", "x": 2, "y": 4, "len": 2, "dir": "v", "bus": {"dx": 0, "dy": -1}}
  ],
  "pickups": [{"id": "p1", "x": 4, "y": 3, "order": 1}],
  "walls": [{"x": 0, "y": 5}],
  "par": 17,                             // 求解器最优步数（3★线）
  "narrowness": 3,                       // 解路径窄度（≤par+2 的解条数）
  "quote": "这谁停的车？"
}
```

- `par` / `narrowness` 由管线写入，游戏端只读不计算——**运行时信任构建期数据**
- `bus.dx/dy`：玩家每完成一步后班车位移向量（确定性，无随机）
- `pickups.order`：第 5 章"按序接送"用；空数组 = 无捎人

### 状态编码（求解器）

- 状态键：各车可变坐标序列 + 已接乘客位图 → 打包为字符串（如 `"1,0,3,2,4|p1"`）；6×6 车辆 ≤14 辆，状态空间实测 ≤ 数万，哈希 Set 足够
- "一步"定义与星级口径：**一步 = 一辆车一次连续滑动（任意格数）**，与实体版 Rush Hour 一致——该定义在 rules/move.js 单点维护

## 五、求解器设计（tools/solver.js）

| 能力 | 算法 | 说明 |
|---|---|---|
| 可解性 + 最优步数 | **双向 BFS** | 正向从初始态、反向从全体目标态（红车在出口行的所有合法位）相遇；毫秒级 |
| 每车必要性 | 逐车剔除重解 | 对每辆车：将其从初始布局移除后重跑双向 BFS，仍可解 → 该关"非最小"，剔除出库。（移除后棋盘变宽松只会更易，检查是充分的必要性判据） |
| 解路径窄度 | 计数 ≤ par+2 的解路径数 | 在 BFS 距离场上做受限 DFS 计数（上限截断 500 防爆炸）；数值越小人类体感越难 |
| 班车关卡 | 复合转移 BFS | 状态转移 = 玩家移动 + 班车确定性推进；班车位置入状态键。注意：班车可能被推入死循环，但状态空间有限，BFS 仍完备终止 |
| 捎人关卡 | 目标谓词扩展 | 目标 = (已接乘客集合 == 全部) ∧ 红车出界；已接集合入状态键（×2^乘客数，仍小） |

**验证基准（测试锚点）**：从 Fogleman 开源数据库抽取 20 个已知最优步数的 6×6 谜题做回归测试——求解器输出必须与已知答案逐一相符，防"自己验证自己"的口径漂移。

## 六、关卡生产管线（tools/pipeline.js）

```
章节配置(chapters.config.js)
  → generator：随机采样布局（rejection sampling：车数/车长/红车行/墙/乘客/班车 按章节带配置）
  → solver：可解性 → 最优步数 → 必要性 → 窄度
  → 筛选入档：按 (步数带, 窄度带) 双指标匹配章节目标曲线
  → 人工抽检：每章 3 关试玩清单（记录表）
  → 产出：levels.data.js + difficulty-curve.svg（50 关双指标曲线图）
```

- 采样效率：6×6 随机布局可解率约 50%+，rejection sampling 完全够快（万级采样分钟内）
- 曲线不达标 → 调章节配置重跑（配置即参数，重跑零成本）——**难度调优 = 改配置，不是手摆关卡**
- 管线每次运行输出 run 报告（JSON：采样数/剔除原因分布）→ 直接进迭代日志

## 七、游戏端要点

### 场景状态机

`boot → title → chapter-map → level → result`；`level` 内子状态：`input / animating / win / dead(无可动感提示)`。

### 输入（手感的第一优先级）

- 指针按下 → 命中车辆 → 跟随拖动（实时预览，带网格吸附）→ 松手落格；另支持点击式（点车再点目标格）双模式，35+ 用户友好
- 移动可撤销？**不做撤销**——Rush Hour 移动全可逆，玩家可手动移回；提供"重开本关"按钮（零成本）

### 渲染与动效

- 单层 Canvas + rAF；车辆滑动用缓动插值（120ms，easeOut）；对象池管理粒子，避免移动端 GC 卡顿
- 动效清单（优先级排序，Day 3 按剩余时间从上往下保）：通关车冲出+道闸 > 捎人上车 > 星级结算 > combo 轻震 > 装饰粒子

### 音效（WebAudio 合成）

引擎起步（低频锯齿短包络）、喇叭（方波双音）、道闸（噪声+滤波扫频）、通关（大三和弦琶音）。静音开关持久化。

### 内置 AI 提示（差异化功能）

卡关求助 → 运行时调用与管线同源的 rules+迷你 BFS → 高亮"当前局面下通往最优解的下一辆车"（给出车不给完整路线，保留思考乐趣）。提示次数有限（见设计方案损失厌恶设计）。

## 十、性能与兼容预算

- 帧预算：60fps（移动端 30fps 下限）；单帧逻辑 < 1ms，渲染 < 8ms
- 包体：dist/index.html ≤ 200KB（当前估算 ~90KB：JS ~60KB + 关卡数据 ~30KB）
- 兼容：iOS Safari 15+ / Chrome 90+ / 微信内置浏览器（X5/WKWebView）；触屏 44px 最小命中区；`touch-action: none` 防滚动穿透；安全区适配 `env(safe-area-inset)`
- 断点续玩：localStorage 每关结算即写，刷新零丢失

## 十二、技术风险与预案

| 风险 | 缓解 |
|---|---|
| 班车+捎人叠加使 BFS 状态膨胀 | 5 章内该组合 ≤5 关，且班车数 ≤1；实测若 >1s 则对组合关降级用单向 BFS+步数上限 |
| 手机浏览器 AudioContext 需用户手势激活 | 首次触摸统一 unlock；静音状态默认安全 |
| 微信浏览器 localStorage 被清 | 存档轻量（<1KB），丢失仅损失进度；提供"选关全开"调试参数 `?free=1`（试玩者用） |
| 单文件拼接引入作用域污染 | build.js 用 IIFE 逐模块包裹 + 严格模式；拼接后冒烟测试 |
| 3 天工期溢出 | 砍序（沿用设计方案 v1.0）：班车 → 7×7 → 每日挑战 → combo 反馈 |
